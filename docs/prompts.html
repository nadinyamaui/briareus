Prompts & memory

Three separate things share this corner of the settings page: the prompts this app sends out on your behalf, the saved prompts library the composer inserts from, and the memory the agents keep between sessions on a project.

Prompts

What this app sends out is a setting, not a string in the source: the pull request description ✎ PR Body Summary writes, and the errand behind every other action and review step.

Three steps, first non-empty wins

  1. The built-in text this app ships with.
  2. The shared text under Prompts in the settings sidebar.
  3. The project's own, under Prompts in its form.

The most specific non-empty one wins, so configuring nothing behaves exactly as it always did, and overriding one prompt for one repository leaves every other prompt and every other repository alone.

Placeholders

A prompt is plain text with {{TOKEN}} placeholders. The editor lists the ones that particular prompt is composed from underneath the field. A token nobody recognises is left in the text exactly as written, which is how a deploy-link template's own @{{PULL_BRANCH}} survives untouched.

Four are common to almost all of them:

Token Is
{{REPO}} owner/name of the repository.
{{PR_REF}} "pull request #12", or "the open pull request for branch x" when the number is not known yet.
{{PR_NUMBER}} The pull request number, or <number> when it is not known yet.
{{BRANCH}} The pull request's own branch, checked out in this workspace.

↧ Load the text it falls back on fills a field with what is being sent today, so editing one line does not mean retyping the whole prompt.

Three strings are deliberately not editable

The test sheet's anchor, the required-fixes anchor and the [reviewer-fix] commit line (lib/markers.js). They are a contract with pull requests that already exist, and changing one makes every PR written before the change unreadable.

Writing one

  • Start from ↧ Load the text it falls back on and edit, rather than writing from scratch. The built-in prompts carry a lot of hard-won detail about how to talk to gh.
  • Prefer the project's own field over the shared one when the instruction is about that repository (its labels, its deploy links, its review conventions).
  • Prefer the shared field for house style that applies everywhere, and leave the project fields empty so a new repository inherits it.
  • For "do this too, at the end", the project form already has purpose-built fields: Publish steps, Test sheet closing steps, Feedback closing steps, which append to the shipped prompt rather than replacing it. Reach for those before overriding a whole template.

Saved prompts

A different, simpler thing: a library of reusable kickoff texts for the composer. No {{TOKEN}}s: they are inserted into the message box exactly as written.

  • The 📋 Prompts menu next to the composer's chips lists them, the current project's own first, then the ones offered on every project, and a click drops the text into the message box.
  • Save current text as prompt… in the same menu adds whatever is typed there.
  • Edit, re-scope to a project or delete them under Saved prompts in the settings sidebar. Lower Order numbers are listed first.

Memory

What the agents keep between sessions on a project: the dashboard's stand-in for Claude Code's own memory directory, which the headless runs it spawns never see (every session is a fresh clone with a fresh config dir).

Memories live in the database, one row per fact, scoped to the repository: a kebab-case name, a type, a one-line description and a body. Every turn's briefing carries the project's memories: newest first, whole until a size budget, then by headline alone.

The fields

Project

Which repository's sessions read it. A memory belongs to exactly one project.

Type

user: who the user is. feedback: how to work. project: ongoing work and constraints. reference: URLs and tickets.

Name

One fact per memory. Folded to a slug on save; the same name on the same project is one memory, so re-saving updates rather than duplicating.

Description

One line, used to judge relevance when the briefing has to choose what to include whole.

Body

The fact itself. Every session on the project reads this in its briefing.

How the agents write them

Every turn can add to the project's memory, and each binary is given the ability differently:

  • Claude and Codex get memory_save, memory_list, memory_read and memory_delete as tools, from a tiny MCP server (lib/memory-mcp.js) mounted per turn.
  • Grok and opencode, which take no MCP server headless, are told the same thing over HTTP: $REVIEWER_MEMORY_URL/api/agent/memories with $REVIEWER_MEMORY_TOKEN as a bearer token, both in the turn's environment. The token is the session's own, minted per process, never stored, and it only reaches that session's project.

Read, correct or prune what was remembered under Memory in the settings sidebar. Editing what an agent got wrong is the point of the panel existing.

What is worth remembering

Things the repository does not say and a fresh clone cannot discover: which of two similar test suites is the one that matters, that a service is stubbed locally, a decision the team made and its reason. Not code structure or git history: the agent can read those.
