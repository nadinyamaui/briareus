Documentation

Run coding agents against your repositories, in parallel, without them standing on each other.

Briareus is a local dashboard for chatting with coding agents: Claude Code, Codex, Grok, opencode, or any provider you register on top of those CLIs. Every session gets a workspace clone of its own and, when its project asks for one, a database server of its own, so two sessions never share a working tree or a schema. You describe what to build; the agent edits, runs the app and its tests, and pushes a branch or opens a pull request when asked.

A session edits files, runs the project's setup and run commands, and pushes to GitHub with the credentials this machine already has, so anything that can reach the port can do all of that. The server listens on 127.0.0.1 only, and the login is off until npm run set-password has been run (the boot log says login: OFF when it is). What it is

The dashboard is served at /. A session is one conversation with one agent, on one branch of one repository. It holds resources for as long as it stays open and hands them back when you close it:

  • A workspace clone. Taken from a pool of slots named <owner>__<repo>, then …__2, …__3 as concurrency demands. Slots are never deleted, so vendor/, node_modules/ and framework caches survive between sessions and only the first run on a fresh clone pays the full setup cost.
  • A database server, if its project asks for one, taken from the servers you register under Database pool, claimed exclusively. The project's database is created on it if it does not exist yet.
  • An app port, one per pool slot (8101, 8102, …), so ▶ Run can serve this session's checkout against this session's database while another session serves its own.

Everything else (the conversation, the log, the per-turn cost ledger) lives in MySQL and survives restarts. Nothing is capped or trimmed.

How a session runs

  1. Claim resources

    An idle workspace slot is taken, and a database server with it when the project claims one. A session that already knows its branch prefers the idle slot still on that branch: the one whose dependencies and build output are already the right ones.

  2. Prepare the checkout

    The default branch is fetched and checked out onto a session branch (dev-<id>), the project's .env template is written in, and the setup commands run. A dependency install is skipped outright when its manifests are byte-for-byte what they were the last time it succeeded in that slot; builds and anything touching the database run every time.

  3. Chat

    Every message spawns one headless provider run that resumes the provider's own session state. Output streams into the page live. The session keeps its clone and its database server between turns.

  4. Run it

    ▶ Run serves the session's checkout with the project's run commands, on the session's own port, against the session's own database.

  5. Watch the pull request

    If the session's branch gets a pull request, its state and CI checks are mirrored into the header and the right panel: at the end of every turn, every 20 seconds while a turn runs, and once a minute otherwise. With a public hostname configured, GitHub webhooks deliver it instead of the timer polling for it.

  6. Close

    Closing releases the clone slot and the database server; the conversation stays readable. Deleting also removes the record and its log, but not its entry in the cost ledger.

Nothing on GitHub starts a session

Worth saying plainly, because much of the rest follows from it: no push, no label and no webhook delivery ever opens a session. A code review is always somebody pressing a button, on the pull request board or in a session composer. Webhook deliveries only refresh panels that are already open.

The nearest thing to an exception is a loop you armed yourself: a review loop reviews the session's own pushes round after round until a review finds nothing. Its trigger is still the session's own turn ending, on a loop its user switched on.
