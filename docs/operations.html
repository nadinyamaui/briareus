Operations

Running it for real

Everything that stops being optional the moment this install is reachable by something other than your own laptop: the two authentication gates, the tunnel, the webhooks, and the maintenance the workspace pool and the schema need.

Reaching it from anywhere

The server listens on 127.0.0.1 only. BIND_HOST moves it, and a container is the only install with a reason to. To use the dashboard from a phone, put a tunnel in front of it rather than opening the port; a Cloudflare tunnel (cloudflared) pointed at localhost:4300 is what this is set up for. Then set PUBLIC_BASE_URL to the public hostname. That one setting is what the test-run video links point at and what turns the webhooks on.

Two gates, because this app runs shell commands as you

Anything that reaches it can start a session, which means running coding agents on this machine with its git and GitHub credentials. One gate is not enough.

1. At the edge

A Cloudflare Access application on the hostname, with a policy that allows only your own email. Add a second application for <hostname>/webhooks with a Bypass policy: GitHub cannot sign into your Access account, and its deliveries authenticate themselves (below).

2. In the app

npm run set-password

Writes a username, a scrypt hash of the password and a cookie signing secret into .env; every request then needs the login (see lib/auth.js). Restart for it to take effect.

Until both keys are set the boot log says login: OFF. Do not leave it that way while the hostname is reachable.

Webhooks

With a public https hostname, the pull request state an open session mirrors is delivered instead of polled for.

Route Sender Authenticated by
POST /webhooks/github GitHub X-Hub-Signature-256, HMAC-SHA256 over the raw body
POST /webhooks/session/:id anything you point it X-Briareus-Signature-256 (HMAC-SHA256 over the time sent and the raw body, with the session's key) or Authorization: Bearer with that key
POST /webhooks/session/:id/instructions a bridge relaying only your own messages the same two ways, with the session's instructions key

The secret is generated on first boot and kept in the app_settings table, so there is nothing to paste anywhere. The app installs its own repository hook on every project it works on (the repo scope the token already needs covers it), recognising its own by URL so an existing deploy hook is never touched, and re-pointing it if the hostname changes.

Nothing is started by a delivery. The hook subscribes to pull_request, pull_request_review, issue_comment, check_suite and status (not check_run: a repository hook hears a suite finish, not a run start), and each refreshes the pull request panel of any open session on that branch as the event lands, rather than on the next twenty-second tick (a commit status still pending refreshes nothing). A repository whose hook has delivered within the last hour, and which this boot found or left carrying every one of those events, is polled only every fifteen minutes as a safety net, which is most of what keeps the GitHub rate limit intact; one that goes an hour without a delivery, or whose older hook could not be updated, is back on the minute sync.

The sync timer remains as the fallback. Nothing about a laptop-only install changes: no public hostname means no hook, and the timer keeps the panels fresh.

To rotate the secrets, delete the webhooks row in app_settings; the hook is rewritten at the next boot, and every session webhook key changes. One session's key is rotated from its ⚡ Webhook dialog, without touching the row.

Session webhooks are the one delivery that starts work. They are how a system outside the dashboard (a support platform relaying what a customer wrote, an alert, a CI) wakes one conversation with a message. A session's webhook is off until you arm it: ⚡ Webhook in the session header arms it, shows the URL and the key, and sets the caps its turns run under. The key is derived from a master secret, the session id and an epoch, so it opens that one session and no other, and rotating it ends it without touching any other session's. Only a session somebody talks to can be armed: not a worker, not a review, fix or QA session.

What arrives is information, never your word. A delivery answers no question: while the agent stands on one, it is held until you have answered. It joins no turn: it waits for the turn under way to end (and after ■ Stop, for your next message), then everything held goes to the agent as one turn of its own, waking the session if it was closed. The agent is told whose words these are not, the text sits between two lines carrying a mark drawn for that message, and no < in it opens a tag. A server registered in allow mode under SSH asks for approval in a turn a delivery started, unless the session's webhook is set to let it run.

Each armed session has three caps: deliveries an hour (30), turns in a row with no word from you (10) and, when you set one, dollars in 24 hours. Past the first the sender gets 429 and a Retry-After; past the others the webhook pauses, says so once in the transcript and is listed in /attention, until you say anything in the session or the spend frees up. An orchestrator's project budget is a cap as well, and so is a turn that a delivery started and that failed.

Send JSON {"text": "…", "source": "ci", "id": "run-4711"}, plain text, or any other JSON (handed over as it came), up to 20,000 characters. source is a label, not an identity; id (or X-Briareus-Delivery) names the delivery, so a retry is answered as the duplicate it is. A signature covers X-Briareus-Timestamp (in seconds), a dot and the raw body, and is refused once it is five minutes old. The answer is 202 with running or held, 200 for a duplicate, 401 for a bad key (whether the session exists or not), 404 for a deleted session, 409 when the webhook is off or the session cannot be woken now, 413 for a message too long and 429 at a cap.

Instructions are the second route, and they are your word. Tick Take instructions too in the dialog and the session gets /webhooks/session/:id/instructions, with a key of its own: the key to the first route never opens it, nor the other way round, and Rotate key ends both. What it delivers goes to the agent the way a message typed in the dashboard does: it answers the question the agent stands on, queues behind a turn under way and lifts the pause the turns in a row put on deliveries. It is for a bridge that decides by who wrote a message where it goes, a WhatsApp relay say: your own number to /instructions, everybody else to the first route. The hourly and spend caps hold for both, and a turn an instruction started still asks before an SSH command in allow mode (nobody is at the dashboard to see it). The answer is 202 with running or queued, and 409 while instructions are off.

The workspace pool

Settings → Workspaces lists every clone slot: its branch, its HEAD, whether it is dirty, its size, its dependency trees, and which open session holds it. A slot is claimed for as long as the session in it stays open, so the two actions only work on idle ones:

Reset setup

Forgets the install fingerprints in the clone's .git/reviewer-setup.json, so the next session runs every setup command again. The right button after a toolchain change the manifests do not reflect.

Clean

Also removes vendor/ and node_modules/. Reclaims the disk, and costs the next session a full install.

Idle clone slots are removed when Briareus starts and once every 24 hours. Slots claimed by open sessions are always skipped.

Database migrations

The app's own schema lives in migrations/, Laravel-style: one timestamped file per change, each exporting up and down, run once in name order and recorded in the migrations table with the batch that applied it (umzug underneath, mysql2 as the only driver).

The server applies pending migrations at boot, so a fresh checkout still only needs a running MySQL. The same thing is available from the shell: 

npm run migrate                   # apply every pending migration
npm run migrate:rollback          # undo the last batch
npm run migrate:status            # what has run, what is pending
npm run make:migration add_x_to_y # write migrations/YYYY_MM_DD_HHMMSS_add_x_to_y.js

2026_08_27_000000_baseline.js is the schema as it stood when this started, written idempotently so a database from before then just gets its row in migrations.

Never edit a migration that has shipped

Add a new one. A file that already ran will not run again.

Deploying

Nothing here deploys itself: no poller watches main and nothing restarts the server on its own, so a commit never picks the moment the live checkout changes under whoever is using it. By hand, on purpose: 

cd /path/to/briareus
git pull --ff-only
npm ci                     # only when package-lock.json moved
npm run build:css          # every pull: the stylesheet is not committed
sudo systemctl restart briareus.service

briareus.service is whatever unit you wrote to run npm start; this repository ships no unit for the app itself, since the checkout path, the user it runs as and the tunnel in front of it are all yours to decide.

public/app.css is Tailwind output and is not committed, so the pull carries the source and not the CSS. npm run build:css is what turns one into the other, and node server.js never does it for you; Tailwind is a dev dependency, so the install has to be a plain npm ci rather than --omit=dev. The container deploy has no such step, since the image builds the stylesheet in a stage of its own, and the documentation site has none either: a Pages workflow builds docs/docs.css and publishes the folder.

Running the pool's MySQL datadirs in RAM has its own units and script; see Keeping them in RAM and deploy/README.md.

Health and observability

  • GET /healthz: a liveness endpoint that also touches the database.
  • GET /api/dev/usage?repo=owner/name: the month's sessions, agent time, tokens and cost, the same numbers the project dashboard shows.
  • GET /api/dev/usage/all?period=month|prev|all: the same ledger across every project, which is what the main 📊 dashboard draws.
  • Settings → Providers: each entry's account, plan, auth state, discovered binary and, for a plan that meters itself, its usage bars: 5-hour and 7-day for a claude or codex subscription, 5-hour and daily for a Z.AI coding plan, credits over the billing period for grok.
  • The boot log: which binaries were found, whether the login is on, migrations applied.

A hardening checklist

  • npm run set-password has been run, and the boot log no longer says login: OFF.
  • The hostname is behind Cloudflare Access, allowing only your own identity.
  • /webhooks has its own Bypass application, and nothing else does.
  • BIND_HOST is still 127.0.0.1 outside a container.
  • The GITHUB_TOKEN is scoped to the repositories this install actually works on.
  • The R2_* keys, if used, are in the process environment rather than .env: that file is readable by every command a session runs.
  • Project .env templates carry development credentials only.

Security problems in Briareus itself go through private reporting, never a public issue.
