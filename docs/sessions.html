Working

Sessions

A session is one conversation with one agent, on one branch of one repository, holding a workspace clone and, when its project asks for one, a database server, for as long as it stays open.

Starting one

＋ New session in the sidebar opens the welcome pane. Above the message box is a row of chips; they are the whole configuration of the session, and they lock once it starts.

On a phone the sidebar is a drawer behind ☰, so the top bar carries its own ＋ beside it: the same action, without opening the drawer first from a board or an open session. It is hidden on wide screens, where the sidebar is a column and its button is always on show.

⌗ Worktree / ⌂ Local / 🧭 Orchestrator / ⚡ Zeus

Where the session works: a fresh workspace clone of its own, this machine's existing checkout, no checkout at all (a supervisor that starts worker sessions), or a read-only clone from which Zeus turns a brief into a GitHub epic. See Local mode and Zeus mode.

Project

Which repository, and with it every setting on the project.

Branch worktree only

A searchable dropdown of the repository's branches. Left on New branch, the session cuts dev-<id> from the default branch. Pick an existing one to continue somebody's work; the session will find the open pull request for it by itself.

Provider / Model / Effort

Which provider entry runs the turns, and on what. The model and effort lists are that provider's own.

🔁 Review loop

Arms the review loop on this session. On the welcome pane it speaks for the next session; over an open session it arms or disarms that session's loop on the spot.

🎬 QA loop

Queues a QA run behind an armed review loop. It starts when that loop converges by declaring no findings.

📋 Prompts

The saved prompt library: insert one into the message box, or save what is typed there.

Files can be attached with the 📎 button, or pasted or dropped straight into the message box.

What happens before the agent sees your message

  1. An idle workspace slot is claimed, preferring one already on the branch you picked.
  2. A database server is claimed, if the project asks for one.
  3. The default branch is fetched; the session branch is checked out.
  4. The project's .env template is written into the checkout.
  5. The setup commands run, in order. Dependency installs are skipped when their manifests are unchanged since the last success in that slot; builds and database steps always run.
  6. Only then is your message handed to the agent.

The first run against a fresh clone is the slow one. After that, vendor/ and node_modules/ survive in the slot and the installs are skipped outright.

Turns

Every message spawns one headless provider run that resumes the provider's own session state. Output streams into the page live over SSE; runs of tool calls collapse into an openable block; the turn's footer shows its tokens, its agent time and, when the CLI reports one, its cost.

■ Stop in the header kills the running turn. The session keeps its clone and its database server between turns and while idle.

The status dot beside a session in the sidebar says what it is doing: running, preparing or queued (pulsing), idle (green), waiting (idle but the agent left a question standing, so it is your move), interrupted, or failed. Beside the provider is a second box with the branch the session works on; clicking it opens that branch's pull request and its runs instead of the conversation.

▶ Run

Serves the session's checkout with the project's run commands, on an app port of its own (one per workspace slot, 8101, 8102, …) against the session's own database, and opens it in a new tab. Two sessions can be served at once without either noticing the other.

The pull request panel

If the session's branch gets a pull request, its state and CI checks are mirrored into the header and the right-hand panel. Synced at the end of every turn, every 20 seconds while a turn is running, and once a minute otherwise, and the panel redraws from a pushed session record, so it never waits for a poll. With a public hostname, GitHub delivers the events instead.

A session finds its own pull request. Being handed a branch that already has one is the normal way to continue somebody's work, and an agent typically reports back "pushed to dev-x (PR #51)": a number, never a URL. So a session on a branch of its own asks GitHub which pull request is open from exactly that branch: when its workspace is prepared, before any review round it would otherwise skip for want of one, and on the sync tick while it has none (that last one on a few minutes' cooldown, since a session can work for an hour before opening anything, and the token is shared with the board and the webhooks).

Nothing is guessed. The match is on the head ref, never on a local session or the repository's default branch. When a branch has several pull requests open at once (GitHub allows that when their bases differ) only the one targeting the branch the workspace was cut from is taken; anything still ambiguous is left unattached, with a line in the session saying which pull requests it could not tell apart.

A pull request found this way is a weaker claim than one you handed the session, in one place: merging it does not close the session. An errand pointed at a pull request still ends the moment it merges, but a session opened to keep iterating on a branch is told and left alone rather than stopped mid-work by a teammate's merge.

🔗 Link PR repairs a missed association. Enter a pull request number, #number, or its full GitHub URL. The dashboard reads the pull request before linking it and refuses one from another repository or head branch. The ✎ beside the session heading edits the conversation title without sending a message to the agent.

Closing, reopening, deleting

  • Close releases the workspace clone and the database server. The conversation stays readable.
  • Reopen claims a clone and a database server again and resumes the conversation.
  • 🗑 Delete also trashes the record and its log. The cost ledger keeps its numbers: deleting a session removes its transcript, not its statistics.
  • The sidebar's multi-select mode closes or deletes several at once; ctrl-clicking a session does the same thing.

A merge ends every errand on a pull request. As soon as any session mirroring it sees merged, every open session working on that pull request (review, errand, QA) is closed: its turn is killed and its resources go back to the pool.

Local mode

The workspace chip switches a session from ⌗ Worktree to ⌂ Local: the agent works directly in the project's existing checkout on this machine: the path configured as Local checkout in the project's settings.

Nothing is prepared. No clone, no branch juggling, no .env seeding, no setup steps, no pooled database. The tree, whatever branch it has checked out, and its real local database are used as they stand. One local session at a time per checkout; the branch picker and ⌕ Code review only apply to worktree sessions.

Zeus mode

Selecting ⚡ Zeus opens the model picker immediately. Choose two models to perform the same complete task independently; the session model in the composer is ZEUS, the summarizer. New Zeus sessions require both choices. Resuming an older session without complete choices also opens the picker before sending the next message.

Both models receive exactly the same complete prompt, investigate a read-only repository clone and return a complete epic. The server refuses different proposal prompts within the same user brief, including after a restart. Models do not receive specialist assignments or see each other's outputs. In the sidebar they appear as Model 1 and Model 2.

ZEUS reads both outputs in full and combines them into one epic, preserving useful unique findings, removing duplicates and checking contradictions against repository evidence. Assumptions and unresolved decisions stay explicit. There is no separate validator: ZEUS consolidates the result and publishes the parent issue with linked implementation sub-issues. The document follows the Zeus epic template under Prompts, overridable per project.

It is your working tree

Uncommitted work in that checkout is in the agent's reach, and nothing rolls it back when the session closes. Local mode is for the times you want exactly that; otherwise use a worktree session.

The project view

Clicking a project name in the sidebar opens its own view instead of a chat, with three tabs:

  • 📊 Dashboard: what this project spent this calendar month, in sessions, agent time, tokens and priced cost.
  • ⇅ Pull requests: the board, holding this project's open pull requests and the errands they are asking for, filtered by author and label, with the provider and model every errand started from here runs on. See Code review & QA.
  • ⊙ Issues: this repository's open issues, each with who reported it, who holds it, its labels and the open pull requests that say they close it (a pull request in another repository is drawn as owner/repo#n so it cannot be read as this one's). Every row carries ▶ Start: it opens a session on the project that reads the issue with gh, implements it on a branch of its own and opens a pull request closing it, with the review loop armed. That session appears in the sidebar badged New branch, and the board stays where it is, so several issues can be started in a row. The issues ride on the board's own query, so opening the tab costs no extra GitHub request, and the walk is bounded at four pages of the most-recently-updated issues: the tab says so when it was cut short. The token needs Issues: read for any of it; without that the board still works and the tab prints what it is missing.
  • Epics are GitHub's own sub-issues, read off the parent/child link rather than an epic label or an [Epic] title. A sub-issue is drawn nested under its parent, in number order, and an epic carries how much of itself is finished (3/8 done) and a fold to put its children away. That count is GitHub's, over every sub-issue: the closed ones and any in another repository or past the four-page walk are in it, which is why it is often larger than the rows nested underneath. A sub-issue whose epic is not on the list — closed, in another repository, or hidden by the pickers — stays where it is and links to it instead. ▶ Start on an epic asks first — and asks what to run it on: an account, model and effort for the orchestrator, and another set for the workers it will start (the project's worker runtime from Settings when one is set, the orchestrator's own picks otherwise). It then opens a 🧭 orchestrator rather than a coding session: it lists the open sub-issues itself and takes them one at a time, a worker each with the review loop armed, merging each pull request (squash) once the loop approves it and its checks are green before the next worker starts. Each review round's findings come to the orchestrator first, to triage against the sub-issue and the epic; only what it keeps is implemented. A loop that stalls hands it the leftover findings to judge the same way: the ones that apply go back to the worker, the rest it waives on the pull request.
  • Self-healing. The dashboard is software too, and an orchestrator can be failed by it: a worker tool that errors or misleads, a briefing that sent a worker the wrong way, a loop that misbehaves. When the dashboard's own repository is set up as a project and flagged as the dashboard itself (Projects), every orchestrator gets a fix_tooling tool beside spawn_worker: it starts a worker on that project, review loop armed, with the orchestrator's report as its brief. The fix is a worker in every other respect: it counts among the open workers and against the budget, it opens a pull request, and the orchestrator merges it (squash) once the loop approves and the checks are green, then says so. The running dashboard keeps its current code until you redeploy it. In the sidebar the worker is drawn under its orchestrator badged 🩹 tooling, and again at the top of the dashboard project's own list, where its branch lives. With no project flagged, the briefing asks the orchestrator to report such flaws to you in a line instead.

Each tab keeps its own filter picks, so narrowing the issues to a label does not throw away the author the pull requests were narrowed to. Switching projects drops both, since a name that means something on one repository means nothing on the next.

What a session costs

Every finished turn is written to a project-owned turn_usage ledger: agent time, tokens in and out, and the provider's own cost figure when its CLI reports one: claude and opencode do, codex does not, and the ledger stores no number nobody charged.

The ledger is independent of the session record, so deleting a session removes its transcript but keeps its statistics. The session header shows that session's tokens and cost as a chip, each turn's footer shows its own, and the project dashboard shows the month so far. The same numbers are available as JSON:

A session's chip and its Context usage panel count everything it ordered, not only its own turns: an orchestrator's numbers cover every worker it spawned, and a task's cover the review sessions, fix sessions and QA run its loops started, while those are open and after they close (an auto-closed review pays its spend into the session it reviewed for as it is deleted). The panel says how many other sessions are in the total. The sub-agents a turn forks inside the CLI were always in that turn's own figures. The ledger stays per turn and per activity, so the dashboard still tells review spend from orchestration spend. 

GET /api/dev/usage?repo=owner/name

The main dashboard

The 📊 button beside ＋ New session opens the same ledger with no project filter: headline tiles, tokens over time, a row per project and a breakdown per model. Its picker chooses the window every number on the page is over: This month, Last month or All time. A month is charted a bar per calendar day, all time a bar per month, both cut on this machine's own clock. Projects you have since switched off are still listed: one disabled mid-month spent what it spent, and leaving it out would stop the rows adding up to the totals.

A cost total wears a + when some of the turns behind it could not be priced at all, so an unpriced turn cannot be read as a free one, and a ~ when some of them were priced by the dashboard rather than by their own CLI: their tokens at the model's published list price, from the models.dev catalog the app fetches once a day and caches. The Cost tile and every cost tooltip say how many turns of the total that was. An estimate is arithmetic over tokens, never an invoice: the ledger itself still stores only what the providers reported. Same numbers as JSON: 

GET /api/dev/usage/all?period=month|prev|all

Where the history lives

Session history and logs live in MySQL (jobs / job_events) and nowhere else, so they survive restarts and nothing is capped or trimmed. Writes are batched and retried while the database is unreachable, and flushed on shutdown. The only files the app writes are the scratch prompt files each turn hands to the CLI, kept in the OS temp directory and deleted when the turn ends.
