Configuration

Environment reference

.env in the app root, read by lib/config.js and nothing else. It is split in two halves on purpose: the required keys each name something about this machine and have no defaults, and the optional keys are behavior that reads the same on every install and do keep theirs.

A missing required key stops the boot

By name, in the message. A default for "which database" or "what this install is called from outside" is a guess at somebody else's setup that fails quietly rather than loudly, so there isn't one. Changes need a server restart.

Required

GitHub

GITHUB_TOKEN

A classic PAT with repo, or a fine-grained token with Pull requests: read/write and Contents: read. Used by the sessions' gh CLI, by the branch → pull request / CI sync in the session header, and by the repository webhook the app registers for itself. Adding Issues: read turns on the project view's ⊙ Issues tab; without it everything else works as before and that one tab says what it is missing. A classic repo token already carries the permission.

Server

PORT e.g. 4300

Where the dashboard listens. The --port command-line flag beats it, so a test instance can run alongside the real one.

PUBLIC_BASE_URL

The public origin of this install, e.g. https://reviewer.example.com behind a Cloudflare tunnel. Two things read it: the video links a test run leaves on a pull request, and the GitHub webhook URL the app registers for itself.

A localhost or .test hostname is a valid answer: it is treated as no public hostname at all, and everything stays polled.

WORKSPACE_DIR ../worktrees

Where the session clones are kept. Relative paths resolve against the app root, absolute paths are taken as they are. Keeping it next to this repo rather than inside it is what stops a session from having the app's own tree inside its workspace.

TEST_VIDEOS_DIR ../test-videos

Where a QA test run drops its scenario videos. Same path rules.

Claude

CLAUDE_MODEL

The model this install runs on by default. Not discovered on purpose: model names age out, and one baked into the code would keep being sent months after it was retired.

CLAUDE_EFFORT

The default reasoning effort to run it at.

The app's own database

Session history, the projects, the providers, the prompt templates, the memories and the cost ledger. The database and its tables are created on first run. Not the same thing as the per-session pool.

Key Example
DB_HOST 127.0.0.1
DB_PORT 3306
DB_DATABASE reviewer
DB_USERNAME root
DB_PASSWORD may be empty, but the key has to be there

"No password" and "you forgot" are not the same answer, which is why an empty value is fine and a missing line is not.

The dashboard's own login

AUTH_USERNAME

The username the login asks for.

AUTH_PASSWORD_HASH / AUTH_SECRET written by a script

A scrypt hash of the password and a random secret that signs the session cookie. Written by npm run set-password, never by hand.

With either of them missing the login is off and anything that reaches the port is trusted: fine on a laptop, not fine behind a public hostname. The boot log says login: OFF.

Optional

BIND_HOST 127.0.0.1

Which interface the server listens on. Loopback only, because the way this install is meant to be reached from outside is a tunnel pointed at it, not an open port. A container is the one place to change it: there the port lives in a namespace of its own and docker compose decides who may reach it.

AUTH_SESSION_DAYS 30

How long a signed-in browser stays signed in.

The CLIs

CLAUDE_BIN / CODEX_BIN / GROK_BIN / OPENCODE_BIN

Auto-discovered; override only if the discovery misses. Which binary each provider entry runs, its isolated login, its custom endpoint and its model list live in the database and are edited at Settings → Providers; only these four binaries are hardcoded.

Per-session database pool

DB_POOL_ENABLED true

Switches claiming off entirely. The servers themselves are rows in the database, added at Settings → Database pool; which projects claim one, and which database name a session uses on it, is per project.

DB_POOL_WAIT_TIMEOUT_MIN 30

How long a session waits for a server to free up before giving up.

DB_POOL_POLL_SECONDS 10

How often it re-checks while waiting.

Developer sessions

DEV_MAX_SESSIONS 3

Only for the projects that claim a pooled database server, and only as the fallback for when the pool cannot answer: claiming off, or no servers configured yet. Otherwise the number of servers is the cap. A project with its database switched off holds nothing exclusive and may open as many sessions as it likes.

DEV_TIMEOUT_MIN 60

Per turn, not per session, and only for a session that claimed one of the pooled servers, since that claim is what its peers queue behind. A session without one (Local mode, or a project with the pool off) is in nobody's way and its turns run without a time limit.

The review loop (🔁)

REVIEW_LOOP_MAX_ROUNDS 3

How many review rounds one armed loop runs before it stops and hands what is left back to you. The last round still reviews and still lists its findings on the pull request; it just does not start another fix session. Without a cap a loop can keep reviewing the code its own fixes introduce: each round genuine, each round smaller, none of them the feature. 0 removes the cap and leaves only the stall gate.

REVIEW_LOOP_LOW_UNTIL_ROUND 1

The last round on which a low finding is still implemented. From the round after it, lows are recorded on the pull request as optional instead of costing a fix session and another review, since a low found late is nearly always a note on the previous round's fix rather than on the change under review. 0 never tightens, so every round implements everything it finds.

Shared video links (Cloudflare R2)

Off by default: the scenario videos then stay on this machine, served at /videos behind the dashboard's login, which means a video link on a pull request only works for whoever holds that login, while the tunnel is up. Set all five keys and every test run composed from then on links its videos from the bucket instead: public, no login, alive when this machine is not.

Key From
R2_ENDPOINT https://<account-id>.r2.cloudflarestorage.com
R2_ACCESS_KEY_ID An R2 API token with Object Read & Write scoped to this one bucket, nothing wider.
R2_SECRET_ACCESS_KEY
R2_BUCKET The bucket name.
R2_PUBLIC_BASE_URL The bucket's public side: its r2.dev URL, or the custom domain connected to it.
  • Videos still land in TEST_VIDEOS_DIR first; the server mirrors them when the recording turn ends, so a link may trail the PR comment by a few seconds.
  • Access control is the link itself (each run's path carries a random 128-bit token) so the bucket must not be listable, which an R2 public bucket already is not.
  • Half the keys is refused at boot: a bucket the app can upload to but no public hostname (or the reverse) would be links pointing at videos that never arrive.
Prefer the process environment for these five

Alone in this file, the R2_* keys may be exported in the server's environment instead of written here. The difference matters: .env is readable by every shell command a session runs, while the environment is stripped of R2_* before it reaches any job child. The Docker setup already does this on its own.

Not in the file at all

Projects (repositories, setup steps, PHP version, database, .env template, run commands), providers, the database pool, the prompt templates, the saved prompts and the memories all live in the database and are edited in the UI. So does the GitHub webhook secret, generated on first boot into the app_settings table, so there is nothing to paste anywhere.
