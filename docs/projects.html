Configuration

Projects

A project is everything the app needs to know to run a session against one repository: which install steps to run, which PHP to run them with, whether a session claims a database server of its own, what to seed the checkout's .env with, and how to serve the app. One row per repository, edited at /settings/projects.

Creating one

  1. Open the form

    /settings/projects, then ＋ New beside Projects in the sidebar. (/settings redirects here.)

  2. Fill in what you know

    Only Repository is genuinely required. Everything else has a sane empty behaviour, described field by field below. A project with nothing but a repository name clones it, runs no setup, seeds no .env, claims no database and cannot be ▶ Run, which is exactly right for a repository you only ever review.

  3. Save

    The in-memory copy every session reads from is refreshed on write, so the change applies to the next session immediately. A session already running keeps the configuration it started with.

The ⧉ button in the header clones the open project into a new entry: the fast way to add a second repository that shares a toolchain. 🗑 deletes it.

Project

Repository owner/name

The GitHub repository, spelled exactly as GitHub spells it. Cloned over HTTPS with the machine's own git credentials. The app injects none of its own, so whatever credential.helper points at is what authenticates.

This string is the project's identity everywhere else: the workspace slots are named after it (owner__name, owner__name__2, …), and the pull request board, the usage ledger and the memories are all keyed on it. Changing it on a saved project effectively makes a different project.

Label

What the project dropdown shows. Cosmetic: leave it empty and the repository name is used.

Local checkout absolute path

This machine's own checkout of the repository. A session started in ⌂ Local mode works directly in it: no clone, no branch juggling, no .env seeding, no setup steps, no pooled database. The tree, whatever branch it has checked out, and its real local database are used as they stand.

Leave it empty to keep Local mode off for this project. One local session at a time per checkout. See Local mode.

This project is the dashboard itself Orchestrator section

Tick it on the repository whose code is running right now, and on no other: a second flag is refused, naming the first. It is what gives every 🧭 orchestrator its fix_tooling tool: a worker on this project, review loop armed, briefed with a flaw the orchestrator found in the tooling running it. The worker runs on this project's worker runtime when one is set, and its pull request is merged by the orchestrator once the loop approves and the checks are green. Redeploying is yours. See self-healing.

Setup

Setup commands one per line

Shell commands run in the checkout, in order, after the branch is prepared and the .env written, before the agent gets your first message. The first failure aborts the session. 

composer install --no-interaction --prefer-dist
yarn install
php artisan migrate:fresh --seed
yarn build

Installs are fingerprinted. A dependency install (composer install, yarn/npm/pnpm install) is skipped outright when its manifests are byte-for-byte what they were the last time it succeeded in that slot and what it installs is still on disk. The fingerprints live in the clone's .git/reviewer-setup.json; Reset setup under Workspaces forgets them.

Builds and anything touching the database run every time, which is why migrations and seeding belong here rather than being something the app does for you. They run against whichever server the session claimed.

PHP bin directory

Prepended to PATH for everything this project runs: the setup commands, the run commands and the agent's own shell. This is how two projects on one machine can want different PHP versions. 

/usr/bin
~/.phpenv/versions/8.4/bin

Leave empty for the machine's own PHP.

Database

Two independent decisions live here: which database name a session uses, and whether it gets a server to itself.

Database

What DB_DATABASE is set to in the session's environment, which beats the checkout's .env. The name must be a plain identifier (A–Z a–z 0–9 _ $), since it goes into DDL, where a placeholder cannot.

With the pool on, the session claims a server and this database is created on it if it does not exist yet.

With the pool off, every session gets a database of its own, this name plus the session id, created on the server the .env template points at, and written into the checkout's .env.

Leave empty to use the .env template exactly as written.

Postgres extensions one per line

Created in the session's database right after it is. A fresh Postgres database carries only what template1 does, so a migration declaring a vector column fails without this; the extension itself must already be installed on the server. Ignored on MySQL.

Give each session a database server of its own checkbox

The switch that makes this project's sessions claim from the database pool. Ticked, a session takes one server exclusively for as long as it stays open, and its peers queue behind the pool's size.

Unticked, the project holds nothing exclusive and its sessions are never capped: they all talk to whatever the .env template points at, each in a database of its own if you named one above.

This checkbox also decides whether the project is capped at all, and whether its turns get a time limit: only a session holding a pooled server is in anybody's way, so only those obey DEV_MAX_SESSIONS and DEV_TIMEOUT_MIN.

Restore from .sql pool only

A dump on this machine, piped into the database every time a server is claimed, right after the database is created, before the setup steps run. Leave empty to skip. Shown only while the checkbox above is ticked.

What the session's environment gets

The claimed server is injected as DB_HOST / DB_PORT / DB_DATABASE / DB_USERNAME / DB_PASSWORD into every command the session runs, and that beats what the checkout's .env says. Write the template for a developer's machine; the pool overrides it where it matters.

Code review

This section is about the errands the app runs on this project's pull requests: who the board is about, what the reviews run on, and what happens after one. Code review & QA covers the workflow itself.

PR author github username

The filter the pull request board applies, deciding whose pull requests this project's board is about. A login, not a display name.

Provider / Model / Effort

What a ⌕ Code review started from the board opens on, unless the composer picks something else. The three selects are dependent: the model and effort lists are the chosen provider's own.

Publish steps

Sent to the agent as its own turn after a code review: this text and nothing else. It is the review's own follow-through, in the review's conversation and on the review's provider, which is why it has no runtime of its own. 

Publish the review to the PR with gh, then move the labels.

Leave empty to run no turn after the review.

Write a test sheet when the 🎬 QA errand is started checkbox

The QA session's first turn derives a manual test sheet from the diff and posts it as one editable comment on the pull request. Ticking it reveals a Provider / Model / Effort row for that step alone; a step left unset runs on whatever the session it came from runs on.

Execute the test sheet and record a video of each scenario checkbox

A second turn serves the app against the session's own database, drives every ⬜ scenario with Playwright, records a video of each and writes the results back into the sheet. Same per-step runtime row.

Where those videos are linked from depends on whether R2 is configured; see Shared video links.

QA notes

Appended to both the test sheet and test run prompts: logins, tenants, URLs, whatever a tester needs that the repository does not say. 

Login admin@example.test / secret, tenant demo, app lives under /app
Test sheet closing steps

Appended to the end of the 📋 Test sheet prompt: what this project wants done once the sheet is on the pull request. Leave empty to add nothing.

Feedback closing steps

Appended to the end of the ⚙ Implement feedback prompt: what this project wants done once the review comments are implemented.

Checkout .env

.env template

Written into the clone as .env before the setup steps run, on every session. Leave empty to use whatever the repository ships. 

APP_ENV=local
APP_DEBUG=true
APP_KEY=base64:…
APP_URL=http://127.0.0.1:8101

DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=my_app
DB_USERNAME=root
DB_PASSWORD=

Write it for an ordinary developer machine. When the session claims a pooled server, the DB_* keys are overridden in the environment anyway; the template is the fallback, not the source of truth.

This file is readable by everything the session runs

Every shell command the agent runs is in the checkout. Put development credentials here, never production ones.

Prompts

This repository's own wording for any prompt the app sends out. One textarea per template, built from the same catalog the shared editor uses. A field left empty falls back to the shared text under Prompts in the sidebar, which in turn falls back to the text this app ships with, so configuring nothing behaves exactly as it always did.

Full explanation, including the {{TOKEN}} placeholders: Prompts & memory.

Run

Run commands one per line

What ▶ Run executes in the checkout. Chained, so the last one is the server that keeps running; the ones before it are the preparation it needs.

Two placeholders: {port} is the session's app port (one per workspace slot: 8101, 8102, …), {dir} is the checkout. 

php -S 127.0.0.1:{port} -t public server.php
yarn build
node server.js --port {port}

Leave empty and the ▶ Run button has nothing to do. The QA test run needs these too: it serves the app the same way before driving the scenarios.

Rules of thumb
  • Anything that has to happen on every session goes in Setup commands; the app provisions the database and nothing else.
  • Anything that has to happen once per clone is not configurable: dependency installs figure that out themselves from the manifests.
  • If the app cannot be served, leave Run commands empty rather than half-filling it: QA's test run depends on it working.
  • Tick the database pool only if sessions genuinely collide; a project with it off is uncapped and cheaper.
