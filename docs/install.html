Getting started

Installation

Two ways in. Install it on the machine, where a session can use whatever toolchain that machine already has, or run the Docker image, which carries the runtime, the CLIs and a MySQL and asks only for a GitHub token.

Requirements

Linux

Developed and run on Ubuntu, including under WSL2. Sessions spawn shell commands and resolve binaries through which; a hit on a mounted Windows drive (/mnt/…) is deliberately ignored, because that is a host binary and not one this Linux can run.

Node.js 24 .nvmrc

The only version supported or tested, and what .nvmrc pins. Also git on PATH.

MySQL 5.7+ or MariaDB 10.2+

For the app's own storage: the projects, the providers, the prompt templates, the session history and the cost ledger. The database and its tables are created on first run; the schema is a set of migrations in migrations/, applied automatically at boot. See Migrations.

This is not the same thing as the per-session database pool, which is a separate list of servers you register in the UI.

At least one agent CLI, authenticated

The Claude Code CLI is the default. The CLI a session spawns does not share the desktop app's login, so sign it in with claude auth login, or put a claude setup-token result / ANTHROPIC_API_KEY where the provider entry can reach it. The Codex, Grok and opencode CLIs are optional and auto-discovered. See Providers.

A GitHub token GITHUB_TOKEN

A classic PAT with repo, or a fine-grained token with Pull requests: read/write and Contents: read, plus Issues: read for the project view's ⊙ Issues tab. Used by the sessions' gh CLI and by the pull request / CI sync in the session header.

A git credential helper

Pushes and fetches authenticate through the machine's own helper: gh auth setup-git, git-credential-libsecret, or whatever credential.helper points at. The app injects no git credentials of its own.

Installing on the machine

  1. Clone and install

    git clone https://github.com/nadinyamaui/briareus.git
cd briareus
npm install
npm run build:css

    The stylesheet is Tailwind output and is not committed, so the build is part of the install: the server serves public/app.css as it stands and never builds it, and a clone that skips this step comes up with every page unstyled. Run it again whenever you pull.

  2. Write the .env

    Copy the example and fill in the required half. Every setting above the optional line names something about this machine (its database, its port, what it is called from outside, which model to run) so none of them has a default. A missing one stops the boot with its name in the message rather than coming up on a guess. 

    cp .env.example .env

    The minimum is a GITHUB_TOKEN, the PORT, a PUBLIC_BASE_URL (http://localhost:4300 is a valid answer, read as "no public hostname"), the WORKSPACE_DIR / TEST_VIDEOS_DIR paths, the CLAUDE_MODEL / CLAUDE_EFFORT pair, the five DB_* keys and an AUTH_USERNAME. Full list on the Environment reference.

  3. Start it

    npm start                 # http://localhost:4300

    --port 4301 (or PORT in .env) moves the server; the flag wins over the file, so a test instance can run alongside the real one.

  4. Turn the login on

    Optional on a laptop, mandatory the moment anything but localhost can reach it. This writes a username, a scrypt hash of the password and a cookie signing secret into .env; restart for it to take effect. 

    npm run set-password

  5. Configure it

    The rest happens in the UI: a provider to run sessions on, database servers if your projects want one each, and at least one project. Your first session walks through all three in order.

Where the clones go

WORKSPACE_DIR defaults to ../worktrees, next to the app's checkout, not inside it. That is deliberate: a workspace inside the app's own tree would put the app's source into every session's working directory. Relative paths resolve against the app root; absolute paths are taken as they are.

In Docker

The image carries node, git, the gh CLI, the four agent CLIs and the mysql/psql clients, and brings up a MySQL of its own beside it. All it needs from you is a GITHUB_TOKEN in the environment, or in the .env next to compose.yaml, which docker compose reads by itself, so an install that already has one is configured. 

GITHUB_TOKEN=ghp_… docker compose up -d --build
docker compose exec app npm run set-password
docker compose restart app

The dashboard comes up on http://localhost:4300.

The knobs

Variable What it does
GITHUB_TOKEN The only required one. Also configures gh as the credential helper inside the container.
HOST_PORT Moves the published port. It stays bound to 127.0.0.1.
PUBLIC_BASE_URL The hostname a tunnel puts in front of it. Turns webhooks and shareable video links on.
DB_PASSWORD Used by both the app and the MySQL beside it.

Configuration still arrives as .env

lib/config.js reads that file and nothing else, so the entrypoint (docker/entrypoint.sh) writes one from the environment on every boot. It lives on a volume, not in the image, and the keys the environment does not name (the login set-password writes, anything added by hand) are carried across each rewrite. Mounting your own file over /app/.env switches all of that off and uses the file as it is.

The volumes are the install

Volume Holds
home The provider CLIs' logins, so claude/codex/grok stay signed in across a rebuild, and the isolated homes opencode entries run in.
state The .env.
workspaces The session clones.
dbdata The session history and everything else in the app's own database.

Removing them is what starting over means.

The database pool in Docker

The extra MySQL servers a session claims are a compose profile of their own, and are not started by default: 

docker compose --profile pool up -d

Then add them at Settings → Database pool as db-pool-1:3306 and db-pool-2:3306; the app reaches them by service name. Their datadir is tmpfs; see Keeping them in RAM.

The image does not carry your project's toolchain

It has enough to run a session, but a project's setup steps run whatever is on PATH, so reviewing a PHP repository means adding php and composer to the Dockerfile. One more thing behaves differently in here than on a machine: pushes authenticate through gh as the credential helper, configured by the entrypoint from the same token.

What the first boot does

  • Reads .env and refuses to start if a required key is missing, naming it.
  • Connects to the app's MySQL, creating the database and applying pending migrations.
  • Discovers the agent CLIs on PATH, the npm global prefix and the native installer paths.
  • Generates the GitHub webhook secret into the app_settings table if it is not there yet, so there is nothing to paste anywhere.
  • Logs whether the dashboard login is on. login: OFF means anything that reaches the port is trusted.
