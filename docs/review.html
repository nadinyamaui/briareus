Working

Code review & QA

Reviews, fixes and manual QA, all driven from a project's pull request board. Configured in the Code review section of the project form.

Every review is somebody pressing a button

Nothing on GitHub starts a session by itself: no push, no label and no webhook delivery ever opens one. The only automatic rounds are inside a review loop you armed, and even there the trigger is the session's own turn ending.

The pull request board

Click a project in the sidebar and open the ⇅ Pull requests tab. It lists the project's open pull requests and the errands each is asking for, filtered by author and label; the header's provider and model selects decide what every errand started from here runs on. ⟳ re-reads GitHub.

A project's PR author setting is the default filter, deciding whose pull requests this board is about.

The ⊙ Issues tab beside it lists the repository's open issues and the pull requests already answering them, on the same query the board makes. Its one errand is ▶ Start, which puts a session on the issue with the review loop armed; on an epic it opens a 🧭 orchestrator that works the sub-issues one at a time and merges each once its loop approves it. See The project view.

The errands

Button Does
⌕ Code review Reviews the branch and publishes what it found on the pull request.
✎ PR Body Summary Writes the pull request description, in the shape the PR body prompt asks for.
📋 Test sheet Derives the manual QA checklist from the diff and posts it as one editable comment.
🎬 Run test sheet Starts the QA session: write the sheet, execute it, record the evidence.
🛠 Implement feedback Works from the pull request's own review threads and pushes the fixes.
✍ Give feedback Sends what you type into the dashboard to the agent as the whole prompt.
🔀 Solve conflicts Merges the base branch in, resolves and pushes.
🧪 Fix failing checks Reads the red CI run and fixes what this branch broke.
🧹 Delete my comments Removes everything the configured GitHub account left on the pull request.

Every one of these is a prompt you can rewrite, shared or per project; see Prompts.

What a code review does

  1. It says it started

    As soon as the clone is claimed, before the minutes the checkout takes, the session comments on the pull request: which agent is reviewing which branch, and that the findings land there when it is done. One anchored comment per PR (<!-- reviewer:review-started -->), so a project reviewing every push edits the notice already there instead of stacking one per push. Best effort: no token, no PR number or a GitHub that will not answer leaves a line in the session's log and the review runs anyway.

  2. It reviews

    On the project's review runtime (provider, model and effort) unless the composer picked another.

  3. It publishes

    The summary comment ends with a machine-readable findings block. Then the project's Publish steps run as one more turn in the same conversation, on the same provider: label moves, issue updates, whatever the team's workflow asks for.

  4. It closes itself

    A review session started from a board row hands its workspace clone and its database server straight back, and its record goes with them, rather than leaving one dead conversation per review in the sidebar. What it found is on the pull request, which is where it gets read and answered.

    The exception is a review that stopped to ask something: it stays open until somebody answers it.

Each fix commit ends with a [reviewer-fix] line, so the dashboard can tell a push it made from one a human made.

The findings panel

The findings themselves live on the pull request. GitHub is the source of truth, and the app only parses the block the review left there. What the app owns is your verdict on each one, stored per finding and mirrored back onto the pull request as one anchored Required fixes checklist comment.

Verdict Means
fix Goes on the Required fixes checklist. A fix session implements it and ticks it.
optional Acknowledged, not required. Left off the checklist and never sent back to be fixed.
dismissed Rejected. Same: off the checklist, never re-sent.

Findings are keyed by a hash of their title: the one thing the block, the stored verdict and the checklist comment all carry. So a verdict survives the next review re-declaring the same finding: your decision stands, however often a later review raises it again.

The review loop

The composer's 🔁 chip arms a review loop, and 🛠 Implement feedback, started from the board, arms the same loop so the fixes it pushes get reviewed. A review, a QA run, any other board errand or a local session is never a loop.

An armed session works its task as usual. Then, round after round:

  1. It settles idle with new commits on its open pull request.
  2. The app starts a review session for it: the same auto-closing kind the board starts, on the review runtime the project configures.
  3. When that review closes, whatever findings it declared are handed to a fix session of its own: the same auto-closing implement-feedback errand the board starts, on the session's branch and provider.
  4. That fix session pushes and closes, which triggers the next review.

The session is the durable half. It is the loop's anchor: it keeps its clone, its database server and its conversation, and you can keep chatting in it undisturbed while the reviews and the fix sessions come and go around it.

Each round's findings are listed on the Required fixes checklist before the fix session starts, exactly as if you had decided them by hand in the findings panel: handing them over to be implemented is that decision. The fix session then ticks the ones it actually fixed, replies on the threads it addressed and resolves them, so the pull request and the panel both show what is solved and what is still open. A finding you had already dismissed or marked optional is left off that list.

A worker's loop is triaged by its orchestrator first. When the worker files under a 🧭 orchestrator, each round's findings reach the orchestrator as an update, each with the loop's own advice on it (what the rules below would have parked, and why), and nothing is implemented until it rules on every one with triage_findings: fix goes to the fix session, dismissed is recorded like a verdict given by hand in the findings panel and said on the pull request with the reason, so no later round offers it again, and optional keeps it on the pull request without spending a round. The orchestrator has the task's whole context, which the review did not. The loop holds until it rules (the worker shows awaiting triage); a loop whose orchestrator was closed meanwhile runs the round the way a loop with no orchestrator does.

When it stops

It runs until it converges: it stops on its own when a review declares no findings, and the 🔁 chip stops it whenever you decide the rounds are no longer paying for themselves.

Three gates keep it from reviewing the code its own fixes introduced, which is the runaway the stall gate below cannot see: every round finds something genuine and something new, so the loop neither runs dry nor repeats itself.

Gate Does
REVIEW_LOOP_MAX_ROUNDS
3		 How many rounds one armed loop runs. The last one still reviews and still lists what it found; it just does not start the fix session that would open the next round. 0 removes the cap.
REVIEW_LOOP_LOW_UNTIL_ROUND
1		 The last round on which a low finding is still implemented. After it, a low is recorded instead of costing a fix session and another review: a low found late is nearly always a note on the previous round's fix rather than on the change under review. 0 never tightens.
Off-diff findings A finding naming a file the pull request does not change is parked. A review reading the whole repository occasionally reports something real about code the branch never touched. It fails open when the diff cannot be listed: withholding a real finding is the worse half of that trade.

A finding held back by either of the last two is recorded as optional: it stays in the findings panel and in the review's own comment on the pull request, stays off the required-fixes checklist, and is not offered again next round. A verdict you gave by hand wins over all of it: a dismissed finding never comes back, and one you marked fix is kept however low it is or wherever it points.

Then there is the stall gate. A round that hands back exactly the findings the round before it did means the fix session between them did not move the review, and implementing them again would push another commit, open the commit gate and start the same round over, so the loop stops there and says so instead of ping-ponging on a session nobody is watching. What it found stays on the pull request, and the next push you make yourself picks the loop back up.

Between rounds a commit gate keeps a session with nothing new pushed from being reviewed again, so chatting never re-triggers a review, and a failed or stopped review pauses the loop until the next push instead of retrying itself in a circle.

Arming mid-session

The 🔁 chip stays live over an open session and turns its loop on or off there and then, which is usually when you know you want it: the task turned out bigger than it looked, or the pull request is up and there is no reason to press ⌕ by hand every push. Arming mid-session reviews what is already pushed rather than waiting for the next push.

Turning it off stops any further rounds; a review already running still finishes and publishes on the pull request, it just reports nothing back. Re-arming starts the round count over, except that a review still running from the arm you turned off is adopted as the new loop's first round, rather than a second review of the same pull request being started alongside it.

QA, once the code is approved

QA is not part of the review, and it is not started by a label either: the board shows a 🎬 QA button on an approved pull request and somebody presses it. It runs in a session of its own: a review session would otherwise have to sit on its clone and its database server for however long the sign-off took.

  • With Write a test sheet on, that session's first turn derives the manual test sheet from the diff and posts it as one editable comment.
  • With Execute the test sheet on, a second turn serves the app against the session's own database, drives every ⬜ scenario with Playwright, records a video of each and writes the results back into the sheet.

Nothing follows the run: the ❌ rows are there to be read, and ⚙ Implement feedback is the errand that acts on them.

The test run needs the project's run commands to work: it serves the app the same way ▶ Run does. Where the videos are linked from depends on whether R2 is configured; without it they are served at /videos behind the dashboard's login.

The QA loop

The composer's 🎬 chip queues a QA loop behind an armed review loop. It is one run, not another series of rounds: when the review loop converges by declaring no findings, the app starts the same kind of auto-closing QA session the board's 🎬 button starts.

  • That session's first turn writes the test sheet.
  • As soon as that turn settles, its second turn executes the sheet and records the evidence.
  • If every executed scenario passes, the QA loop stops.
  • Failed scenarios are reported back to the task session as QA feedback, and the loop stops there too, since acting on that feedback stays a human decision for now.

Turning the review loop off also cancels the QA run waiting behind it.

Merged pull requests

A merge ends every errand on a pull request. As soon as any session mirroring it sees merged, every open session working on that pull request (review, errand, QA) is closed: its turn is killed and its clone and database server go back to the pool. The conversations stay readable, as they do after any close.

The one session that survives a merge is one that found its own pull request rather than being handed it: it is told, and left alone rather than stopped mid-work by a teammate's merge.

Setting a project up for review

  1. Fill in PR author so the board shows the right pull requests.
  2. Pick the review Provider / Model / Effort. Reviews are the one place where spending on a stronger model usually pays.
  3. Write Publish steps: at minimum, publishing the review to the pull request with gh. Leave it empty and nothing happens after the review.
  4. For QA: tick the two step checkboxes, fill in QA notes with the logins and URLs a tester needs, and make sure Run commands actually serve the app.
  5. Optionally give the test sheet and feedback errands closing steps: label moves, a ping in chat.
