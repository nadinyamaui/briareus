Operations

Troubleshooting

Symptoms, in the order you are likely to meet them.

It will not boot

A message naming one .env key

That key is in the required half and has no default. Fill it in; the Environment reference says what each one wants. A key present but empty is a valid answer for DB_PASSWORD; a missing line is not.

A MySQL connection error

The DB_* keys point at the app's own database, not the session pool. Check the server is up and the account may create databases; the schema is created on first run.

Half the R2 keys are set

Refused on purpose: a bucket the app can upload to but no public hostname, or the reverse, would be links pointing at videos that never arrive. Set all five or none.

The port is taken

npm start -- --port 4301. The flag beats PORT in the file, so a test instance can run alongside the real one.

The dashboard does not ask for a login

The boot log says login: OFF when either AUTH_PASSWORD_HASH or AUTH_SECRET is missing. Run npm run set-password and restart: the keys are read at boot.

In Docker: docker compose exec app npm run set-password, then docker compose restart app. The entrypoint rewrites .env on every boot but carries across the keys the environment does not name, so the login survives.

A provider will not answer

Status says the binary was not found

Discovery looks at PATH, the npm global prefix and each CLI's installer path. Set CLAUDE_BIN, CODEX_BIN, GROK_BIN or OPENCODE_BIN to the absolute path if it misses.

Under WSL, a which hit under /mnt/… is ignored on purpose, since that is a Windows executable. If your only install is there, install the CLI inside Linux.

The Log in button is missing

It only exists on a saved entry: the login is registered against the row. Save first, then log in.

Logged in in my terminal, but the entry is not

Expected. Each entry has a login directory of its own (~/.claude-provider-<id>, ~/.codex-provider-<id>) so it never disturbs the login you use yourself. Sign the entry in from its form.

Test fails on a custom endpoint

Check the base URL and key together. On claude the key goes out as ANTHROPIC_API_KEY and, with a base URL, also as ANTHROPIC_AUTH_TOKEN, and a gateway reading only one of the two headers is a common cause. On opencode the URL is set on the service the entry's models name, so a model not named <service>/<model> leaves both the key and the URL with nothing to attach to, and the wire the Test speaks is the service's: Anthropic's for anthropic/…, OpenAI's /chat/completions for the rest.

A session will not start

It sits waiting for a database server

Every enabled pool entry is claimed by an open session. Close one, or add another entry: the pool is the session cap. It gives up after DB_POOL_WAIT_TIMEOUT_MIN (default 30).

"Too many sessions" with no pool configured

With claiming off or no servers registered, DEV_MAX_SESSIONS (default 3) is the fallback cap. Register pool entries and it stops mattering.

Setup aborted on the first command

The first failure aborts the session by design. The session log has the command and its output. A missing toolchain is the usual cause; in Docker, remember the image carries node and git but not php, composer or anything else your project needs.

Local mode is not offered

The project has no Local checkout path set. And only one local session at a time per checkout.

Setup runs everything every time

Installs are skipped only when their manifests are byte-for-byte unchanged and what they install is still on disk. So a lockfile that changes on every install, or a node_modules something else deletes, defeats it. Builds and database steps run every time by design.

The fingerprints live in the clone's .git/reviewer-setup.json; Reset setup under Settings → Workspaces clears them deliberately.

The session's database is wrong

  • With the pool on, DB_HOST/DB_PORT/DB_DATABASE/ DB_USERNAME/DB_PASSWORD are injected into the environment and beat the checkout's .env. An app that reads its config from somewhere the environment does not reach will not see them.
  • The database name must be a plain identifier (A–Z a–z 0–9 _ $), since it goes into DDL, where a placeholder cannot.
  • Migrations and seeding are the project's setup commands. The app creates the database and restores the dump; it runs nothing else.
  • The pool account needs CREATE DATABASE, and write access to everything a restored dump contains.

The pull request never attaches

  • The match is on the head ref: the session's own branch. A local session, or a session on the repository's default branch, is never matched: a branch that is nobody's in particular cannot be claimed.
  • When a branch has several pull requests open (GitHub allows it when their bases differ), only the one targeting the branch the workspace was cut from is taken. Anything still ambiguous is left unattached, with a line in the session naming what it could not tell apart.
  • The lookup on the sync tick has a few minutes' cooldown, so a freshly opened pull request can take a moment. It is also looked up at the end of every turn.
  • Check the GITHUB_TOKEN can actually read that repository.

Webhooks are not arriving

  • PUBLIC_BASE_URL must be a real public https hostname. A localhost or .test value is read as "no public hostname" and the hook is never registered.
  • Cloudflare Access must have a Bypass application on <hostname>/webhooks. GitHub cannot sign into your Access account.
  • The app installs the hook itself and recognises its own by URL. Check the repository's webhook deliveries on GitHub for the response it got.
  • To rotate the secret, delete the webhooks row in app_settings; the hook is rewritten at the next boot.
  • None of this is required. Without it the sync timer keeps every panel fresh, just less promptly.

The review loop stopped early

  • It converged. A review declared no findings. That is the success case.
  • The stall gate fired. A round handed back exactly the findings the round before it did, so the fix session did not move the review. The findings stay on the pull request; your next push picks the loop back up.
  • The commit gate. Nothing new was pushed, so no round starts. Chatting never re-triggers a review.
  • A review failed or was stopped. The loop pauses until the next push rather than retrying itself in a circle.
  • There is no pull request yet. A round needs one; the session looks for it before every round it would otherwise skip.

QA videos do not play

  • Without R2, videos are served at /videos behind the dashboard's login, so a link on a pull request only works for whoever holds that login, while the tunnel is up. Configure the five R2 keys for links that work for everybody.
  • Mirroring happens when the recording turn ends, so a link can trail the comment by a few seconds.
  • The test run needs the project's Run commands to actually serve the app.

After a restart, every session says "interrupted"

Expected. A restart interrupts every running session: the boot marks them so and clears their database claims, because claims live in the process and nowhere else. Reopen a session to claim a clone and a server again and carry on; the conversation is intact.

The UI looks unstyled after a change

public/app.css is build output and the server never builds it, so the file is whatever your last build left there, or missing entirely in a fresh clone. Any change that adds, removes or renames a Tailwind class under public/, or edits src/app.css, needs npm run build:css again (npm run watch:css while iterating). Nothing to commit: the deploy builds its own copy. The documentation site is the same with npm run build:docs-css and docs/docs.css.

Still stuck

The session log is the first place to look: it carries the setup commands and their output, which server was claimed, and every line the pull request lookup wrote. After that, open an issue. Security problems go through private reporting instead.
