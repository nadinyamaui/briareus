Configuration

Providers

A provider is one entry in the composer's agent picker: a label, one of three CLI binaries, and whatever that entry needs beyond the binary: its own login, or a custom endpoint with an API key, plus optional model and effort lists. Registered under Settings → Providers.

The model

Four binaries are hardcoded: claude, codex, grok and opencode. Everything else is a row in the database. That split is what lets you have several entries on one binary: a subscription login and an API key, two different endpoints, a cheap model for errands and an expensive one for reviews.

Each entry gets a login directory of its own, derived from its id (~/.claude-provider-<id>, ~/.codex-provider-<id>), with the login mirrored into the row. So signing an entry in never disturbs the claude or codex login you use in your own terminal, and two entries on the same binary can be signed into different accounts.

opencode has no home variable of its own (it reads the XDG base directories), so its entries get an XDG root instead (~/.opencode-provider-<id>), with all four bases inside it. Nothing is mirrored into the row there: an opencode entry authenticates with its API key, which travels in the environment and never lands on disk.

The binaries

Binary Discovered at Override
claude PATH, the npm global prefix, the native installer's path CLAUDE_BIN
codex PATH, ~/.npm-global/bin, /usr/local/bin CODEX_BIN
grok PATH, ~/.grok/bin GROK_BIN
opencode PATH, ~/.opencode/bin, ~/.npm-global/bin, /usr/local/bin OPENCODE_BIN
A note for WSL

WSL inherits the Windows PATH, so which can land on a mounted Windows drive. A hit under /mnt/… is ignored on purpose: that is a host executable, not one this Linux can run. If discovery finds nothing, set the *_BIN override to the Linux path.

Registering one

  1. Settings → Providers → ＋ New

  2. Label and binary

    The label is what the picker shows, so make it say what matters at a glance (Claude (sub), Codex API, Z.AI GLM).

  3. Pick a mode, then save

    The Log in button only exists on a saved entry, because the login is registered against the row: there is nothing to log in until a row exists. Save first, then sign in.

  4. Check the Status section

    A saved entry grows a Status block at the top of the form: the account and organization, the plan, the auth state, which binary was found and where, the login directory, when it was last checked, and, for an entry whose plan meters itself, its usage bars: the 5-hour and 7-day windows for a claude or codex subscription, the 5-hour and daily quota of a Z.AI coding plan, and one bar for a grok login's credits over the billing period. Every one is best effort: a login idle long enough for its token to expire, or an endpoint that has moved, just shows no bar.

The fields

Label

What the provider picker shows. Also what the review runtime selects list.

Binary

claude (Claude Code), codex (Codex), grok (Grok) or opencode. Changing it changes which of the fields below apply.

Mode claude, codex

Login: the CLI's own sign-in, kept in this entry's registered directory. API token: an endpoint and a key instead.

Two binaries have only one of the two, so the select is hidden for them: a grok entry is always a login, and an opencode entry is always a key.

Log in login mode, saved entries

Every login happens in your browser, and each binary does it differently:

  • claude: the server hands the page the claude.ai authorization URL, you approve there, and paste the code claude.ai shows back into the field beside the button. Press Finish and the server exchanges it for the entry's tokens.
  • codex: the server runs codex login hidden; the CLI opens the tab itself and its localhost callback finishes the login. Nothing to paste; the status catches it on its own.
  • grok: a device flow, where the CLI prints a confirm URL, the page opens it, and the CLI polls until you approve.
  • opencode: nothing to log in to. Its entries authenticate with an API key, so the button is not shown.
Base URL token mode

On claude: passed to the CLI as ANTHROPIC_BASE_URL, for a proxy or an Anthropic-compatible endpoint. Leave empty for the Anthropic API.

On codex: a custom API endpoint driven through the codex CLI (Responses wire format). Sessions run with a server-written CODEX_HOME pointing codex at it, so the machine's own ~/.codex login is never touched. This is how a Z.AI / GLM entry is built.

On opencode: the base URL of the service this entry's models name, for a proxy or a compatible gateway. opencode sets an endpoint per service in its config (provider.anthropic.options.baseURL for an anthropic/… model), and the entry's URL is handed to the CLI that way, as an inline config (OPENCODE_CONFIG_CONTENT) next to the key, so nothing is written to the machine's own opencode config. Include the /v1 when the service's own URL carries one. Leave empty for the service's own endpoint.

API token token mode

On claude: passed as ANTHROPIC_API_KEY, used instead of a login. With a base URL it also goes out as ANTHROPIC_AUTH_TOKEN, so gateways that read Authorization rather than x-api-key see it too.

On codex: it authenticates the base URL above.

On opencode: the key for the service this entry's models name, anthropic for anthropic/claude-sonnet-4-5, which is how opencode names a model and keys its credentials. It is handed to the CLI as its whole credential store, so no login is needed and the credentials in your own terminal stay untouched.

Test token mode

Runs the binary against the endpoint and key as entered and reports what came back. An entry that cannot answer here will not answer in a session either.

Models / Efforts one per line

Override the lists the composer offers for this entry. Leave both empty to take the CLI's own: for codex that means reading its models cache rather than a list baked into this app that would go stale, and for opencode the models.dev catalog it caches, narrowed to the one service this entry's key is for.

Useful when an entry only has access to a subset, or when a custom endpoint serves models the CLI has never heard of.

Default model / Default effort

What the composer preselects for this entry. Empty means the CLI's own default.

Common setups

A subscription Claude entry

Binary claude, mode Login, save, then Log in and paste the code. Leave the model list empty. The Status block will show the plan and two usage bars: how much of the 5-hour and 7-day windows this account has spent, and when each resets.

A metered Claude entry beside it

A second entry, same binary, mode API token, base URL empty, key pasted in. Now the composer offers both: run everyday sessions on the subscription and let the expensive parallel reviews go through the key, or the reverse.

GLM through the codex CLI

Binary codex, mode API token, base URL pointed at the Z.AI endpoint and the key beside it, then list the GLM model names under Models. Sessions get a CODEX_HOME written for them, so your own ~/.codex login is untouched. A coding plan meters the key itself rather than a login, so the Status block reads its quota straight off the endpoint: a bar for the 5-hour window and one for the day, each with when it resets.

Different agents for different work

A project's Code review section picks the provider, model and effort its reviews open on, and each QA step (test sheet, test run) can name one of its own. A cheap fast entry writing the test sheet while an expensive one does the review is a normal arrangement.

Where a provider gets chosen

Situation Runs on
A session you start yourself The composer's provider / model / effort chips, locked once it starts.
An errand pressed on the pull request board The board header's provider and model selects.
A ⌕ Code review started from the board The project's Code review runtime, unless the composer picked another.
A QA step (test sheet, test run) That step's own runtime, or, left unset, whatever the session it came from runs on.
The publish turn after a review Always the review's own provider. It is the review's second breath, in the review's conversation, and only the model that ran the review holds that.
