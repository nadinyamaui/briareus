Configuration

Database pool

The list of MySQL servers a session can take for itself. Each entry is one server (host, port, username, password) and one session holds one server at a time, exclusively, for as long as it stays open. Registered under Settings → Database pool.

Why it exists

Parallel sessions used to share one database, so a test that truncated a table or a migration that rebuilt the schema broke whatever else was running at the time. Giving each session a server of its own is the blunt fix, and it is blunt on purpose: nothing about a project's test suite has to be changed for it to work.

Two different databases, do not confuse them

The DB_* keys in .env point at the app's own database: the projects, the providers, the prompts, the session history, the cost ledger. The pool on this page is the sessions' databases, and has nothing to do with those keys. On a single-machine install they are usually different servers, or at least different ports.

Adding a server

  1. Settings → Database pool → ＋ New

  2. Point it at the server

    Host, port, username, password. Press Test connection.

  3. Save

    The capacity counter beside the sidebar heading goes up by one. That number is the ceiling on how many sessions of pool-claiming projects can be open at once.

In the pool: sessions may claim this server checkbox

Untick to take a server out of rotation without deleting it: for maintenance, or while you work out whether it is the one misbehaving. A session already holding it keeps it until it closes.

Label

What the sidebar and the session log call it. Defaults to host:port.

Host / Port

Where the server is, from the app's point of view. In Docker that is the compose service name: db-pool-1, port 3306. Host and port together must be unique across the pool: two entries for the same server would hand two sessions the same database, which is exactly what the pool exists to prevent.

Username / Password

An account that may CREATE DATABASE (the session's database is created on demand) and, if a project restores a dump,, may write everything in it. The password may be empty.

Test connection

Connects with what is in the form right now, saved or not. Do this before saving: a bad entry in the pool fails at the least convenient moment, which is a session that has already spent two minutes cloning.

What happens on a claim

  1. The session picks an idle enabled entry. If none is free, it waits, up to DB_POOL_WAIT_TIMEOUT_MIN (default 30), checking every DB_POOL_POLL_SECONDS (default 10).
  2. The project's Database name is created on that server if it is not there yet. Any Postgres extensions the project lists are created in it.
  3. If the project names a Restore from .sql dump, it is piped in, before the setup steps run.
  4. The server is injected into the session's environment as DB_HOST, DB_PORT, DB_DATABASE, DB_USERNAME and DB_PASSWORD, beating whatever the checkout's .env says. The project's setup commands (migrations, seeding) then run against it.
  5. A line is written into the session log saying which server was claimed.
  6. The claim is released when the session closes, fails or is deleted.

Claims live in the server process and nowhere else. Sessions are the only claimants, and a restart interrupts every session (the boot marks them interrupted and clears their claims) so there is nothing on disk to reconcile.

How many entries do I need?

As many as the number of sessions you want open at once on projects that claim a server. That is the whole rule. A project with the pool switched off holds nothing exclusive and is never capped, so a repository with no database costs nothing here.

When the pool cannot answer the question (claiming switched off with DB_POOL_ENABLED=false, or no servers registered yet) DEV_MAX_SESSIONS (default 3) is the fallback cap. Once there are entries, the pool's size is the cap and that setting stops mattering.

Running the servers

Briareus does not start MySQL for you; it connects to servers that are already running. Three ordinary ways to have several:

Docker compose

The repository's own compose file ships a pool profile:

docker compose --profile pool up -d

Then add db-pool-1:3306 and db-pool-2:3306 as entries.

A templated systemd unit

On a machine with MySQL installed, a mysql-pool@<port> template gives you one instance per port (3307, 3308, 3309 and up) each with its own datadir. Add one pool entry per port.

Keeping them in RAM

A pool server is disposable by design: the app creates the session's database and restores the project's dump before the session runs, so an instance that comes up empty is repopulated on first use. That makes tmpfs the natural datadir: a reboot leaves none of it behind, and the next session gets a server that has never held anybody's data.

scripts/mysql-pool-ram.sh and the units in deploy/ do this for eight instances (3307–3314). The install, the memory sizing and the reset commands are in deploy/README.md.

The master on 3306 stays on disk

It holds Briareus's own database (session history, projects, providers, prompt templates) and none of that is meant to be disposable. Only the pool instances go to RAM.

Rough sizing: an empty instance is around 190 MB and a restored project dump adds a few hundred more, which puts eight of them near 4 GB. The script's RAM_SIZE (3G) and BUFFER_POOL (512M) are per-instance ceilings, not reservations, but they are ceilings eight times over, so size the pool against the RAM you actually have.

The project half

Registering a server does nothing on its own. A project has to ask for one: tick Give each session a database server of its own and name the Database in the project form.

Migrations and seeding stay the project's business, in its setup commands. They run on every session, against whichever server was claimed. The app creates the database and restores the dump; everything past that is yours.

Related settings

.env key Default What it does
DB_POOL_ENABLED true Switches claiming off entirely. With it off, no project claims a server whatever its own checkbox says.
DB_POOL_WAIT_TIMEOUT_MIN 30 How long a session waits for a server to free up before giving up.
DB_POOL_POLL_SECONDS 10 How often it re-checks while waiting.
DEV_MAX_SESSIONS 3 The session cap used only when the pool cannot answer for it.
DEV_TIMEOUT_MIN 60 Per-turn time limit, and only for a session holding a pooled server, since that claim is what its peers queue behind. A session without one runs without a limit.
